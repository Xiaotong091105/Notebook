Plan rationale — request-routing · V2

From benchmark to router: how we pick the best method per request

We don't yet know whether CogStack's methods beat plain SQL, or by how much, for the kinds of requests this team actually gets — and before we can even ask that question, we need to understand each historical request well enough to know what a correct answer looks like. This is the plan for both: understanding and labeling requests first, then finding out which method wins, and turning that answer into something that guides every future request, without assuming a trained model is required to do it.

This project labels requests only, not patient documents. CLEF eHealth-style schemas annotate clinical documents; ours annotates the requests clinicians make, extended with one new idea: which extraction method actually answered each request.

Stage 0 is new in V2: before anything can be benchmarked, requests have to be understood and labeled by hand, since no published schema for classifying requests (as opposed to documents) exists. Stage 3 is still the actual deliverable: a router built from evidence, not guesswork, that costs nothing to run because choosing among methods is free — only running Azure carries a real cost. Stage 5 stays dashed: it starts once there's evidence to justify it, and is then kept up to date rather than treated as a one-off.

The six stages

Grouped into three phases: understand each request, build the router from evidence, then keep improving it.

Phase 1 — Understand

0

Label requests

now

Work through historical requests one at a time, starting with Request 22 (ICI toxicity audit), and label each by hand.

  • Label with an extended CLEF schema — entity, relation, timeline — plus a new extraction method entity: which of SQL / MedCAT / regex / LLM actually answered the request.
  • The clinician judges the best method per search term — a practical, clinician-adjudicated proxy, not a gold standard in the CLEF sense.
  • Write a short learning map per request as part of the same pass.
  • No published schema classifies requests directly; the closest prior art is a cohort-retrieval query taxonomy linking query structure to retrieval-method performance.

Phase 2 — Build the router

1

Benchmark

now

Run SQL, MedCAT concept search, and regex against every request labeled in Stage 0.

  • Run Azure LLM on a sampled subset only, since it's the one method with a real per-call cost.
  • Score each method against the Stage 0 label, not against each other.
2

Analyze

now

Find what distinguishes the requests where CogStack's methods won from the ones where SQL was already good enough.

  • E.g. does it name a specific concept, need negation handling, or need reasoning about timing across documents.
  • This is where "is it worth switching off SQL" actually gets answered, request-type by request-type.
3

Codify as rules

now

Turn those patterns into an explicit, written decision table — this is "the classifier" in practice.

  • Which method to use for which kind of request, backed by the benchmark numbers, not guesswork.
  • Doesn't need to be a trained statistical model to do the job — a rule table is something anyone on the team can read, question, and correct.
4

Deploy + log

now

Wire the rule table into how requests actually get handled, and log every decision.

  • Log whether each decision plus outcome turned out right.
  • Logged outcomes feed back into Stage 0, refining the request labels over time.

Phase 3 — Improve

5

Train a model, then keep refining it

later, revisited continuously

Start training once Stage 0's labels and the deployment log give enough evidence, then keep it up to date as more requests get labeled — not a one-off event.

  • At today's scale (~150–160 labeled requests), published evidence puts reliable minimum sample sizes nearer 500–1,000 — early versions should stay a supplement to the rule table, not a replacement.
  • Use a 70/30 train/test split, not 80/20, while N stays under roughly 1,000.
Why Stage 0 comes before the benchmark ▶

A benchmark can only score methods against something known to be correct. With no existing request-classification schema to lean on, that "known to be correct" has to be built by hand first — one request at a time — before Stage 1 has anything solid to score against.

Why this isn't a gold standard ▶

CLEF/i2b2-style gold standards come from multiple independent annotators with measured agreement. Here, one clinician judges the best extraction method per request — useful for routing, but a single-rater proxy, not verified ground truth, until inter-rater reliability is measured.

Why rules before a trained model ▶

With roughly 150 historical requests spread across a handful of categories, there isn't enough data for a trained text classifier to reliably beat a well-evidenced rule table — and the rule table is auditable in a way a model isn't, which matters when the downstream decision affects a cancer data request.

Why the Azure cost doesn't block this ▶

The router's own decision — which method to use — costs nothing to compute, whether it's rules or eventually a small local model. The Azure cost only applies to the rare request the router actually sends to the LLM, which is precisely what a good router is supposed to minimize, not avoid engaging with.

Strengths and limitations

Strengths

  • Fills a confirmed gap. No published schema classifies data-extraction requests; extending CLEF's structure with an extraction-method entity is a defensible response.
  • Grounded in real operational data. ~150 real historical requests, with real SQL, real outcomes, real clinician feedback.
  • Directly actionable. The request-trait → extraction-method mapping is exactly what the router needs, not a side artifact.
  • Cost- and audit-aware design. Rules before ML, LLM calls minimized, every decision auditable.
  • Reusable beyond this project. A generalized schema could serve other data-clinic teams facing the same routing problem.

Limitations

  • Underpowered for a trained model. ~150–160 requests sits below the ~500–1,000 floor the literature treats as reliable.
  • Single adjudicator, no inter-rater reliability on the extraction-method labels yet.
  • Single-site provenance — generalizability beyond this hospital is untested.
  • Severe class imbalance across the Yellow(4)/Blue(17)/Other(135) request tiers.
  • Hindsight bias risk — labels are assigned with the outcome already known, with no prospective test.
  • Not a real gold standard — a practical routing proxy, not independently verified ground truth.

Reference for Request Schema

Papers informing the request-labeling schema and router

Every paper found relevant during literature search for the Classifier project, each with a brief summary and a 1–5 relevance/importance score for this specific project.

Overview of the ShARe/CLEF eHealth Evaluation Lab 2014 Task 2: Disorder Attributes in Clinical Reports

Relevance

Mowery, D. et al. · CLEF 2014, CEUR-WS Vol-1180 · ceur-ws.org/Vol-1180/CLEF2014wn-eHealth-MoweryEt2014.pdf

Defines the canonical CLEF entity/attribute schema (negation, uncertainty, severity, body location, doc-time class, temporal expression), annotated and adjudicated by two coders. This is the actual source of "CLEF's structure" that Stage 0's schema extends — the most load-bearing citation in the whole reference list.

Recommended use: cite as the primary schema source when writing up Stage 0's methodology; borrow its attribute checklist (negation, uncertainty, severity, body location, doc-time, temporal expression) directly when defining the request-level entity types.

A Query Taxonomy Describes Performance of Patient-Level Retrieval from Electronic Health Record Data

Relevance

medRxiv · medrxiv.org/content/10.1101/19012294v1

A 59-characteristic taxonomy of EHR cohort-retrieval queries, explicitly linked to which retrieval method performs best for each query type. This is the closest existing analogue to Stage 0–2's extraction-method mapping — same idea, applied to cohort queries rather than ad-hoc data-clinic requests.

Recommended use: use its 59 characteristics as a starter checklist when defining request traits in Stage 2's analysis — several of its query-structure features (temporal relations, structured vs. unstructured mix) likely transfer directly to request labeling.

Evaluating temporal relations in clinical text: 2012 i2b2 Challenge

Relevance

Sun, W., Rumshisky, A., Uzuner, O. · J Am Med Inform Assoc, 2013 · pmc.ncbi.nlm.nih.gov/articles/PMC3756270

Defines the EVENT / TIMEX / TLINK temporal-relation schema (adapted from TimeML) that CLEF/i2b2-style "timeline" annotation descends from. Source of the timeline entity in our extended schema, though it's one layer removed from request-level labeling itself.

Recommended use: keep in reserve — reference it only if the flat "timeline" entity needs to become more granular (e.g. splitting into EVENT/TIMEX/TLINK sub-fields); not needed for the current schema's level of detail.

A taxonomy of generic clinical questions: classification study

Relevance

Ely, J. W. et al. · BMJ, 2000;321:429–32 · pubmed.ncbi.nlm.nih.gov/10938054

Classifies clinicians' information needs — not documents — into 64 generic question types, with measured inter-rater reliability. A direct precedent for labeling requests rather than records, and a template for how to close this project's biggest gap: reporting agreement between raters on the extraction-method labels.

Recommended use: follow its inter-rater-reliability reporting method (e.g. Cohen's kappa) once a second labeler is added to Stage 0; also useful as the citation for framing requests as "information needs" in any write-up.

Lightweight Query Routing for Adaptive RAG: A Baseline Study on RAGRouter-Bench

Relevance

arXiv:2604.03455, 2026 · arxiv.org/abs/2604.03455

Evaluates classical classifiers (best: TF-IDF+SVM) routing queries to retrieval pathways from structural/lexical features, and finds medical queries the hardest domain to route. The closest existing prior art to the router itself (Stage 3–5), and its finding — simple features can beat fancier embeddings — is directly actionable when building the eventual trained model.

Recommended use: use as the starting architecture for Stage 5 — try a lightweight classical classifier (TF-IDF+SVM) before anything more complex, since it already outperformed embeddings on a similar routing task.

Determinants of Training Corpus Size for Clinical Text Classification

Relevance

arXiv:2601.15846, 2026 · arxiv.org/abs/2601.15846

MIMIC-III-based study finding ~600 labeled documents sufficient for 95% of max achievable classifier performance, with substantial task-to-task variation. Clinical-domain-specific and directly comparable to our ~150–160 labeled requests — the strongest sample-size citation available.

Recommended use: track Stage 5 performance against N as labeling grows, using ~600 as a rough target size for when the trained model can be trusted; cite when justifying why the rule table stays primary until then.

A method for determining the number of documents needed for a gold standard corpus

Relevance

J Biomed Inform, 2012 · sciencedirect.com/science/article/pii/S1532046411002243

A Poisson-based, word-capture-probability method for estimating corpus size, converging on ~500 documents for 0.95 capture probability in a clinical dictation corpus. A second, independently derived method that lands near the same ~500 floor as the corpus-size paper above — useful corroboration, though less directly about request labeling.

Recommended use: optional — apply its formula if a more rigorous, defensible target sample size is needed (e.g. for a governance conversation), rather than relying on rule-of-thumb figures alone.

On the diminishing return of labeling clinical reports

Relevance

arXiv:2010.14587 · arxiv.org/pdf/2010.14587

Shows label-count-vs-performance curves flattening early for clinical text classifiers. Secondary support for treating ~150 labeled requests as an early checkpoint rather than a finished dataset, complementing the corpus-size papers above.

Recommended use: cite alongside the corpus-size papers when justifying, in any write-up or governance conversation, why ~150–160 requests is an early checkpoint and not a stopping point.

TREC Medical Records Track & Clinical Decision Support Track overviews

Relevance

Roberts, K. et al. and others · TREC 2011–2016 · trec.nist.gov/pubs/trec23/papers/overview-clinical.pdf

Background lineage for cohort/query retrieval evaluation in clinical IR — topic statements use paired long/short query fields, which is a useful request-representation idea, but these are evaluation-campaign overviews, not classification schemas. Background context only, not a schema to build on directly.

Recommended use: background reading only — cite in a related-work section for context on clinical query evaluation lineage; do not build the schema or router directly on this.
