Learning Map

OMOP at UCLH

A mental model for how UCLH reshapes raw Epic clinical data into the OMOP Common Data Model — schema, vocabulary, local catalogue, and the training that gets a researcher from zero to a real query.

01 Essence

What is it fundamentally? OMOP is a Common Data Model (CDM) — a fixed relational schema plus a standardized vocabulary — that reshapes messy, hospital-specific EHR data into one consistent structure. At UCLH, "OMOP" is a whole local stack built around that schema: raw Epic data is transformed into CDM tables, catalogued so people can find what exists, taught to new users, and exported into downstream analysis tools.

Why does it exist? Every hospital records the same clinical reality in a different local schema, using different code systems. OMOP exists so that "find every patient with condition X" is the same query regardless of which hospital's EHR the data came from.

What problem does it solve? Two at once: structural heterogeneity (different tables/columns for the same fact) — solved by the fixed CDM schema — and semantic heterogeneity (the same fact coded differently) — solved by mapping every fact to one standard concept from the OHDSI vocabulary.

What did people do before it? Bespoke SQL against the raw warehouse, rewritten every time the question or schema changed; manual chart review to resolve coding inconsistencies; study-specific extracts nobody else could reuse; a local analyst hand-translating the same protocol at every site in a multi-site study.

What new possibilities does it create? Federated multi-site research where the same analysis code runs unmodified elsewhere; a discovery layer (OMOPCAT) that checks feasibility before a single query is written; community-built tooling reused instead of rebuilt per hospital; one shared training path instead of retraining every analyst on a bespoke warehouse.

02 World Model

Objects

  • CDM tables — PERSON, VISIT_OCCURRENCE, CONDITION_OCCURRENCE, DRUG_EXPOSURE, PROCEDURE_OCCURRENCE, MEASUREMENT, OBSERVATION, DEVICE_EXPOSURE, DEATH, and supporting vocabulary/metadata tables.
  • Concept / concept_id — the atomic unit of meaning: every clinical fact resolves to one standard concept_id, regardless of how it was originally coded.
  • Source value / source concept_id — the original local code, preserved alongside the standard concept for audit and traceability.
  • Vocabulary — the standardized coding systems OMOP maps onto (SNOMED-CT, RxNorm, LOINC, etc.), browsed via Athena.
  • Person_id / visit_occurrence_id — the linking keys that tie every clinical event back to a patient and an encounter.

Actors

  • UCLH Epic — the source EHR where clinical care is actually documented.
  • SAFEHR — UCLH's data/informatics team; builds the Epic → OMOP pipeline and maintains OMOPCAT, omop-course, and omop-carpentries.
  • OHDSI / OMOP CDM working group — the international community that defines and versions the CDM schema and vocabulary.
  • Researchers / clinical analysts — browse OMOPCAT, request or receive an extract, and query it (often via R/CDMConnector).
  • Downstream applications — OMOP_ES and DAP-R, which consume exports for analysis.

Workflows

  1. Epic data is ETL'd into the UCLH OMOP CDM instance, local codes mapped to Athena standard concepts.
  2. A researcher browses OMOPCAT to check concept availability and volume before committing to a study design.
  3. A researcher new to OMOP works through omop-course / omop-carpentries to learn the schema and R tooling.
  4. The researcher exports a defined concept set or cohort from OMOPCAT into OMOP_ES or DAP-R.
  5. Analysis runs against CDM tables using standard OHDSI-ecosystem tooling — in principle comparable to the same analysis at another OMOP site.

05 Search Space Expansion

Beginner questions rarely asked

  • Why can the same clinical event appear as multiple rows across different domain tables?
  • What happens to a fact with no good standard concept — where does it go?
  • Why does OMOPCAT only show counts, not records — what exactly is being protected?

Questions experts ask

  • Is a "missing" concept a true absence, a documentation gap, or an ETL mapping failure?
  • How stable is a concept_id's meaning across vocabulary versions?
  • Where does UCLH's ETL make judgement calls that could bias a downstream analysis?
  • How does data latency (Epic → ETL → CDM → OMOPCAT) affect currency?

Questions worth exploring next

  • What's UCLH's process for requesting a full extract once OMOPCAT confirms feasibility?
  • How does the CDM handle data Epic captures but the base domains don't cleanly fit?
  • What's the update/versioning cadence for UCLH's CDM instance and vocabulary?
  • How does OMOP_ES differ from DAP-R in practice?

Questions that define mastery

  • Can you predict from a question's shape alone whether structured tables suffice, or narrative review is needed?
  • Can you read an OMOPCAT count and correctly infer why it's low, without guessing?
  • Can you design a cohort definition that ports cleanly to another OHDSI site?
  • Can you trace one analysis-ready row in OMOP_ES back to its Epic source and vocabulary mapping?

06 Ecosystem

Upstream

OHDSI's OMOP CDM specification and governance; Athena and the OHDSI standardized vocabularies; UCLH Epic as source-of-truth; the Carpentries lesson framework underlying omop-carpentries.

Downstream

OMOPCAT; OMOP_ES and DAP-R; individual research studies and feasibility assessments; multi-site OHDSI network studies; trained researchers who build cohort definitions and tools on top of CDM data.

Alternatives

Querying the raw Epic/warehouse schema directly (faster for one-off questions, not reusable or comparable); bespoke local data marts (avoid CDM overhead, can't be shared); manual chart review (handles judgement calls, doesn't scale).

Complements

NLP/LLM extraction over clinical narrative, for the judgements structured tables can't make; the R/Python OHDSI tooling ecosystem (CDMConnector, CohortGenerator, FeatureExtraction); UCLH's data governance processes around export and access.

07 Transferable Principles

First principles

  • A common data model trades local fidelity for cross-site comparability.
  • Structured coded data and clinical judgement/narrative are not the same thing.
  • Discovery should precede extraction — check plausible existence and volume before committing to a full request.

Transferable methodologies

  • Resolve the concept in Athena before writing any query — don't guess at codes.
  • Treat "sparse" and "absent" as different findings requiring different investigation.
  • When a question needs judgement the coded data can't express, plan a complementary extraction method rather than forcing SQL to answer it.

Stable vs. changing knowledge

Stable: Epic → standardization → CDM instance → discovery → export → analysis is the durable pipeline shape; the standard-concept-plus-source-value pattern is the core traceability mechanism; OMOP answers "what was coded," not "what was clinically true," structurally, not just at UCLH.

Changing: which CDM version and vocabulary release are current; OMOPCAT's feature set and what's exportable; the current omop-course / omop-carpentries syllabus.

08 Minimum Mental Model

If you remember only these, you retain most of the field's leverage.

  1. 01

    OMOP is a fixed schema plus a standardized vocabulary — it solves "different table structures" and "different codes for the same thing" at once.

  2. 02

    Every fact maps to one standard concept_id, while the original local code is preserved in a parallel source_value.

  3. 03

    Athena is where you look up what a concept_id represents, and the reference for how UCLH's ETL should have mapped a local code.

  4. 04

    The UCLH pipeline: Epic → SAFEHR ETL → UCLH OMOP CDM instance → OMOPCAT (discovery) → OMOP_ES / DAP-R (analysis).

  5. 05

    OMOPCAT shows aggregated, privacy-safe counts so you can check feasibility before requesting real patient-level data.

  6. 06

    PERSON is the identity hub; almost every clinical table links back via person_id, often via visit_occurrence_id.

  7. 07

    Because schema and vocabulary are shared across OHDSI sites, an analysis built for UCLH can, in principle, run unmodified elsewhere.

  8. 08

    OMOP captures the coded record of care, not the reasoning behind it — judgement calls need complementary methods, not more SQL.

  9. 09

    omop-course / omop-carpentries teach the schema plus standard R tooling (CDMConnector, dplyr, duckdb), not raw SQL against Epic.

  10. 10

    A "missing" concept could be true absence, a documentation gap, or a mapping failure — check Athena and the ETL logic before assuming.

09 Common Misconceptions

"OMOP is just UCLH's data warehouse under a different name."
The value is in the standardization, not just having a queryable copy — it's specifically shaped to be comparable with other hospitals' OMOP data.
"If OMOPCAT shows a low count, the data doesn't exist at UCLH."
A low count can mean true rarity, an ETL mapping gap, or a source-documentation gap — it needs investigation, not literal acceptance.
"Athena and OMOPCAT are the same kind of tool."
Athena browses the global, abstract vocabulary; OMOPCAT browses UCLH's actual captured data against that vocabulary.
"Once data is in OMOP CDM, any clinical question can be answered with a query."
OMOP stores coded facts, not clinical judgement or narrative reasoning — attribution and severity grading need a complementary method.
"Learning OMOP means learning SQL against the CDM tables."
At UCLH, the taught path is R-based (CDMConnector, dplyr, duckdb, Parquet) — SQL literacy helps but isn't the primary tool taught.
"A concept_id means the same thing forever."
Vocabularies version and refresh; a concept's mappings or standard/non-standard status can change between releases.

10 Summary

What I truly gain is not the ability to query UCLH's OMOP tables, but a model for how raw Epic clinical data becomes standardized, discoverable, and comparable — via a fixed schema (CDM), a shared vocabulary (Athena), a local discovery layer (OMOPCAT), and downstream analysis environments (OMOP_ES, DAP-R) — and the judgement to know when that structured, coded record is enough to answer a question, versus when it only surfaces candidates that still need clinical reasoning or narrative review to resolve.
